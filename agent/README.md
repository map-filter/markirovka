# markirovka-agent: агент печати этикеток

Небольшая программа, которую клиент (швейный цех) запускает на своём компьютере рядом с принтером этикеток. Агент сам ходит на сервер по HTTPS, забирает задания на печать (этикетки с GS1 Data Matrix) и отправляет их на принтер в RAW-виде, байт в байт. Входящие порты на компьютере клиента открывать не нужно: соединение всегда исходящее.

Один исполняемый файл без зависимостей (Go, только стандартная библиотека). Сборки для Windows, Linux и macOS.

## Как это работает

1. При старте и затем каждые 30 секунд агент шлёт серверу heartbeat: версию, имя компьютера и адрес принтера.
2. Агент делает long-polling запрос `GET /api/agent/jobs/next?wait=20`. Сервер держит запрос до 20 секунд и отвечает либо заданием, либо `204 No Content`.
3. Полученное задание декодируется из base64, проверяется (для ZPL: начинается с `^XA`, содержит `^XZ`) и отправляется на принтер.
4. Результат сообщается серверу: `printed` или `failed` с текстом ошибки.

При сетевых ошибках и ответе 401 агент повторяет запросы с экспоненциальной паузой: 1 с, 2 с, 4 с ... до 60 с. После первого успешного ответа пауза сбрасывается. По Ctrl+C (SIGINT) или SIGTERM агент дописывает текущее задание, отправляет подтверждение и завершается.

## Запуск на Windows

Скачайте `markirovka-agent.exe`, положите, например, в `C:\markirovka\` и создайте рядом файл `start.bat`:

```bat
@echo off
set SERVER_URL=https://label.example.kz
set AGENT_TOKEN=вставьте_токен_из_кабинета
set PRINTER=tcp://192.168.1.50:9100
C:\markirovka\markirovka-agent.exe run
```

Проверка принтера без сервера (печатает тестовую этикетку с текстом и Data Matrix):

```bat
set PRINTER=tcp://192.168.1.50:9100
C:\markirovka\markirovka-agent.exe test-print
```

В PowerShell то же самое:

```powershell
$env:SERVER_URL = "https://label.example.kz"
$env:AGENT_TOKEN = "токен"
$env:PRINTER = "tcp://192.168.1.50:9100"
.\markirovka-agent.exe
```

Для автозапуска положите ярлык на `start.bat` в папку автозагрузки (`Win+R`, `shell:startup`) или зарегистрируйте службу через планировщик заданий (триггер "При запуске компьютера").

## Linux и macOS

```sh
export SERVER_URL=https://label.example.kz
export AGENT_TOKEN=токен
export PRINTER=cups://Zebra_ZD421
./markirovka-agent-linux-amd64
```

В Docker (например, на мини-ПК в цехе):

```sh
docker build -t markirovka-agent:dev .
docker run -d --restart unless-stopped --name markirovka-agent \
  -e SERVER_URL=https://label.example.kz -e AGENT_TOKEN=токен \
  -e PRINTER=tcp://192.168.1.50:9100 markirovka-agent:dev
```

В образе нет `lp`, поэтому из контейнера печатайте через `tcp://` или `file://`.

## Команды и настройки

```
markirovka-agent [run] [флаги]       работа с сервером (по умолчанию)
markirovka-agent test-print [флаги]  тестовая этикетка ZPL на PRINTER
markirovka-agent version             версия
```

У каждого флага есть переменная окружения. Флаг важнее переменной.

| Флаг | Переменная | По умолчанию | Назначение |
|---|---|---|---|
| `-server-url` | `SERVER_URL` | | адрес сервера, `https://...` |
| `-token` | `AGENT_TOKEN` | | токен агента из кабинета |
| `-printer` | `PRINTER` | | адрес принтера, см. ниже |
| `-poll-wait` | `POLL_WAIT` | `20` | сколько секунд сервер держит long-polling запрос (1-300) |
| `-insecure-tls` | `INSECURE_TLS` | `false` | не проверять сертификат сервера, только для разработки |
| `-allow-printer-override` | `ALLOW_PRINTER_OVERRIDE` | `false` | разрешить серверу выбирать другой принтер в задании |
| `-log-level` | `LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error` |

## Принтеры

Адрес принтера задаётся URI:

| URI | Что делает |
|---|---|
| `tcp://192.168.1.50:9100` | RAW-сокет (JetDirect, порт 9100). Порт можно не указывать, по умолчанию 9100. Таймаут подключения 5 с, записи 30 с. Каждая копия отправляется отдельным соединением. |
| `cups://Queue_Name` | Запуск `lp -d Queue_Name -o raw -n <копий>`, данные идут на stdin. Нужен установленный `cups-client` (Linux, macOS). Если `lp` нет, задание завершается понятной ошибкой. |
| `file:///var/labels` или `file:///C:/labels` | Запись в каталог: каждая копия отдельным файлом `<id>-<n>.<ext>`, где n от 1 до числа копий, ext: `zpl`, `pdf` или `bin` (для `raw`). Удобно для отладки и для принтеров с "горячей папкой". Файл пишется во временный и затем переименовывается, поэтому наблюдатель папки не увидит его недописанным. |

Проверенные варианты подключения:

- **Zebra** (ZD220, ZD421, GK420 и др.): сетевая модель по `tcp://IP:9100`; USB-модель через CUPS-очередь с драйвером Raw (`cups://Zebra`). На Windows для USB-принтера проще всего включить общий доступ или использовать сетевую модель.
- **Xprinter** (XP-360B, XP-420B и аналоги с ZPL-эмуляцией или TSPL): по `tcp://IP:9100` или CUPS raw. Для них сервер должен присылать задания в языке, который понимает принтер (ZPL или `raw`).
- **Godex** (G500, EZ-1100): поддерживают ZPL-эмуляцию, подключение так же через порт 9100 или CUPS raw.

Формат `pdf` отправляется как есть, в том числе через `cups://` (тоже с `-o raw`): его напечатает только принтер, который сам понимает PDF. Для обычных термопринтеров сервер должен присылать `zpl` (или `raw` на языке принтера: TSPL, EPL, EZPL).

### Данные не изменяются

Агент передаёт полезную нагрузку байт в байт: никаких перекодировок, замены переводов строк или обрезки. Это важно для GS1 Data Matrix: в данных встречаются разделители групп `0x1D` (GS) и ZPL-последовательности `~1` (FNC1). Тесты проверяют, что такая нагрузка приходит без изменений и в TCP-сокет, и в файл, и на stdin `lp`.

Для формата `zpl` есть проверка здравого смысла: после начальных пробелов данные должны начинаться с `^XA` и содержать `^XZ`, иначе задание помечается `failed` и на принтер ничего не уходит. Для `raw` и `pdf` проверки нет.

### Тестовая этикетка

`test-print` печатает этикетку 50x37 мм (203 dpi) с текстом, GTIN и Data Matrix:

```
^FO240,95^BXN,5,200,0,0,1,~^FD~10104600000000015 21TEST0000001~193TEST^FS
```

(без пробела, он здесь только для читаемости). Качество 200 (ECC 200), `~` задан символом управляющей последовательности, первый `~1` означает FNC1 (GS1 Data Matrix), второй `~1` разделяет поля переменной длины.

## Безопасность

- **Токен.** `AGENT_TOKEN` выдаётся в кабинете на каждый компьютер отдельно, его можно отозвать. Передавайте токен через переменную окружения, а не флаг `-token`: флаги видны в списке процессов. Токен уходит только в заголовке `Authorization: Bearer`.
- **HTTPS.** Используйте только `https://`. Для `http://` агент работает, но пишет предупреждение: токен идёт открытым текстом. `INSECURE_TLS=true` отключает проверку сертификата и нужен только для стенда с самоподписанным сертификатом.
- **Выбор принтера сервером.** По умолчанию поле `printer` в задании разрешено только если оно пустое или совпадает с локальным `PRINTER`; иначе задание отклоняется с `failed`. Если включить `ALLOW_PRINTER_OVERRIDE=true`, сервер сможет отправлять задания на любой адрес из локальной сети клиента, писать файлы в любой доступный каталог (`file://`) и запускать `lp` с любой очередью. Включайте только если доверяете серверу и это действительно нужно (несколько принтеров на одном агенте).
- **Ограничения.** Ответ с заданием не больше 64 МБ, копий не больше 1000. Имя файла для `file://` строится из id задания, все символы кроме латиницы, цифр, `-` и `_` заменяются на `_`, поэтому выйти из каталога нельзя. Имя CUPS-очереди проверяется, параметры командной строки через него не передать.

## Протокол (то, что реализует сервер)

Все запросы с заголовком `Authorization: Bearer <AGENT_TOKEN>`. Адрес сервера берётся из `SERVER_URL` (без завершающего `/`, можно с префиксом пути, например `https://host/app`).

### Получить задание

```
GET {SERVER_URL}/api/agent/jobs/next?wait=20
```

- `200` и JSON:

  ```json
  {"id":"j-123","format":"zpl","copies":1,"printer":"","payload_base64":"XlhBLi4uXlha"}
  ```

  `id` обязателен (строка, в URL подтверждения экранируется), `format` один из `zpl`, `pdf`, `raw`, `copies` от 1 (0 или отсутствие считается за 1), `printer` пустой или URI принтера, `payload_base64` в стандартном base64 с паддингом (RFC 4648, не URL-safe).
- `204 No Content`: заданий нет. Сервер может держать запрос до `wait` секунд; если сервер отвечает 204 сразу, агент сам выдерживает паузу 1 с между запросами.
- `401`: токен неверный или отозван, агент пишет ошибку в лог и повторяет с растущей паузой.
- Любой другой код: ошибка, повтор с паузой.

Клиентский таймаут запроса: `wait` + 15 секунд.

### Подтвердить задание

```
POST {SERVER_URL}/api/agent/jobs/{id}/ack
Content-Type: application/json

{"status":"printed","error":""}
{"status":"failed","error":"connect to printer 192.168.1.50:9100: connection refused"}
```

Ответ 2xx считается успехом. При ошибке агент повторяет подтверждение до 5 раз с паузой, потом сдаётся (в лог). Сервер должен принимать повторное подтверждение одного и того же задания без ошибки.

### Heartbeat

```
POST {SERVER_URL}/api/agent/heartbeat
Content-Type: application/json

{"version":"0.1.0","hostname":"SHOP-PC","printer":"tcp://192.168.1.50:9100"}
```

При старте и каждые 30 секунд. Ошибки только пишутся в лог.

### Что стоит учесть на сервере

- Выдавая задание, помечайте его как "в работе" и не выдавайте повторно, пока не пришло подтверждение или не истёк таймаут (например, 5 минут). Агент гарантирует "не больше одного раза за выдачу", но если подтверждение потеряется, сервер решает сам, печатать ли повторно.
- Одно задание за раз: агент запрашивает следующее только после подтверждения предыдущего.

## Сборка

Нужен только Docker, Go на машине не требуется.

Тесты и проверка:

```sh
docker run --rm -v "$PWD":/src -w /src -e CGO_ENABLED=0 -e GOFLAGS=-buildvcs=false \
  golang:1.23-alpine sh -c 'go vet ./... && go test ./...'
```

Сборка бинарников под разные системы (результат в `dist/`, каталог в `.gitignore`):

```sh
docker run --rm -u "$(id -u):$(id -g)" -e HOME=/tmp -e GOCACHE=/tmp/gocache \
  -v "$PWD":/src -w /src -e CGO_ENABLED=0 -e GOFLAGS=-buildvcs=false golang:1.23-alpine sh -c '
  V=0.1.0
  GOOS=windows GOARCH=amd64 go build -trimpath -ldflags "-s -w -X main.version=$V" -o dist/markirovka-agent.exe .
  GOOS=linux   GOARCH=amd64 go build -trimpath -ldflags "-s -w -X main.version=$V" -o dist/markirovka-agent-linux-amd64 .
  GOOS=linux   GOARCH=arm64 go build -trimpath -ldflags "-s -w -X main.version=$V" -o dist/markirovka-agent-linux-arm64 .
  GOOS=darwin  GOARCH=arm64 go build -trimpath -ldflags "-s -w -X main.version=$V" -o dist/markirovka-agent-darwin-arm64 .
  GOOS=darwin  GOARCH=amd64 go build -trimpath -ldflags "-s -w -X main.version=$V" -o dist/markirovka-agent-darwin-amd64 .'
```

Docker-образ (около 15 МБ, alpine, запуск не от root):

```sh
docker build --build-arg VERSION=0.1.0 -t markirovka-agent:dev .
```

## Структура

```
main.go                  команды run, test-print, version; флаги и переменные окружения
internal/client          HTTP-клиент протокола: задания, подтверждения, heartbeat
internal/agent           цикл опроса, backoff, обработка задания, выбор принтера
internal/printer         принтеры tcp://, file://, cups://, проверка ZPL
internal/label           встроенная тестовая этикетка ZPL
```
